## STEP 4 — usual suspects eliminated

- **Two copies of the mod in `mods/`**: run D deliberately put both jars in `mods/` and the server still reached `Done (`; each of A/B/C/A2/B2/C2 has exactly one mod jar (directory listings printed per run).
- **`-dev` jar instead of remapped release**: the build produced `discord_voice_bridge-1.0.0-all.jar` (19,374,180 B, pre-remap shadow output) and `discord_voice_bridge-1.0.0.jar` (21,161,849 B, remapped release). The jar booted was the latter; its manifest says `Fabric-Mapping-Namespace: official`, `Fabric-Minecraft-Version: 26.3`, `Fabric-Loader-Version: 0.20.1`; the server log reports `discord_voice_bridge 1.0.0`. No `-dev.jar` was shipped.
- **Stale `build/resources/main/fabric.mod.json`**: both CI builds used `./gradlew clean build`; the control/fixed processed resources are preserved in `verification/*build-resources-fabric.mod.json` and differ by exactly this one line (`diff -u`), and the final source expands byte-for-byte to the fixed processed resource.
- **Loader/Minecraft/Java mismatch**: every log prints `Loading Minecraft 26.3 with Fabric Loader 0.20.1`, plus `- java 25`, `- minecraft 26.3`, `- fabricloader 0.20.1` in the mod tree. JDK is 25.0.4.1.
- **Version-string semantics**: run against the real Loader 0.20.1 `VersionPredicateParser` / `SemanticVersionImpl`: `>=0.165.0` matches `0.165.0+26.3` = `true`, matches `0.165.0` = `true`, matches `0.164.9+26.3` = `false`; `>=0.166.0` does not match. Build metadata (`+26.3`) is ignored, so the version constraint was never the problem.
- **Nested Fabric API absent?** No: both installed and final jars contain `META-INF/jars/fabric-api-0.165.0+26.3.jar` (id `fabric-api`, 44 modules) and `fabric-permissions-api-0.7.0.jar`. Run A lists `fabric-api 0.165.0+26.3` as a child of `discord_voice_bridge`.

## Separate finding (NOT the reported bug, out of scope for this one-line fix)

After `Done (`, the mod's `onServerStarted` calls `DiscordVoiceBridgeConfig.load()`, whose `save()` runs `GSON.toJson(this)`. `GSON` is a plain `GsonBuilder` and the class holds non-transient `ReentrantReadWriteLock lock` and `Path configPath` fields. Gson 2.14 on Java 25 refuses reflective access to JDK internals, so `com.google.gson.JsonIOException: Failed making field ... accessible` is thrown in the server tick loop and a crash report is written. This is independent of mod resolution (it happens *after* `Done (`), and every fixed run reaches `Done (` with no dependency error. `--add-opens java.base/java.util.concurrent.locks=ALL-UNNAMED` only moves it to the next JDK field (`sun.nio.fs.UnixPath#fs`), confirming the real fix would be to make those two fields `transient` or serialize a dedicated DTO. Not included here to keep the diff minimal.

Other unrelated stdout noise: OSHI/JNA `NoSuchMethodError` while building the system report (harmless), and `Minecraft Services Discovery` TLS warnings because `discovery.minecraftservices.com` is blocked in the sandbox (offline mode). Neither prevents startup.
